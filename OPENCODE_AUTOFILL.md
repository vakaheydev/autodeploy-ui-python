# AI-помощник формы через OpenCode

Интеграция проверена для OpenCode `1.18.18`. Форма может подключиться к уже
работающему общему серверу либо создать собственный `opencode serve`. В обоих
режимах API доступен только как `http://127.0.0.1:<port>`.

## Сервер

Четвёртая карточка **OpenCode** на главном экране содержит две основные кнопки:

- **Подключиться к серверу** — подключиться к адресу из настроек. Такой внешний
  процесс форма никогда не завершает.
- **Создать новый сервер** — проверить `opencode --version`, выбрать свободный
  порт и запустить дочерний процесс:

  ```text
  opencode serve --hostname 127.0.0.1 --port <PORT>
  ```

Для обоих вариантов показываются этапы подключения, адрес, версия, ownership,
PID и состояние агентов. Кнопка **Проверить состояние сервера** повторяет
`GET /global/health` и `GET /agent` без создания нового процесса. Пока открыт
главный экран, активное соединение дополнительно перепроверяется в фоне каждые
15 секунд; потеря внешнего сервера автоматически скрывает AI-чат.

При старте приложение автоматически пробует подключиться к
`http://127.0.0.1:4096`. Стандартный connect timeout — 10 секунд; адрес и timeout
изменяются на экране OpenCode. Ошибка отключает только AI-функции.

Созданный формой процесс завершается вместе с приложением. Внешний общий сервер
остаётся работать, поэтому к нему одновременно можно обращаться из формы и из
браузера. Все запросы формы получают отдельный `x-opencode-directory`, а каждая
заявка — отдельную session, поэтому браузерные задачи не смешиваются с формой.

## Конфигурация OpenCode и runtime

Глобальный пользовательский `opencode.json` учитывается самим OpenCode. Поэтому
настроенные в нём provider, model и MCP доступны общему серверу и форме.

При этом форма намеренно не запускает OpenCode из каталога репозитория. Она
использует стабильную отдельную runtime-директорию:

- Linux: `$XDG_DATA_HOME/gravitee-autodeploy-ui/opencode-runtime` либо
  `~/.local/share/gravitee-autodeploy-ui/opencode-runtime`;
- Windows: `%LOCALAPPDATA%\gravitee-autodeploy-ui\opencode-runtime`.

В runtime копируются только три файла агентов:
`.opencode/agents/autodeploy-copilot.md`, `.opencode/agents/form-router.md` и
`.opencode/agents/form-extractor.md`. Если OpenCode
понадобятся plugin-зависимости, `.opencode/node_modules` появится именно там, а
не в проекте с формой и не рядом с YAML-файлами с токенами. Путь runtime виден
на экране OpenCode.

Настройки формы:

- server URL, Basic Auth username/password и connect timeout;
- startup/request timeout и максимальный размер очищенного контекста;
- необязательная пара Provider ID + Model ID;
- выбранные MCP из списка, который возвращает `GET /mcp`;
- конкретный сервер JSON Repository MCP;
- чекбокс, разрешающий агенту **запрашивать** `git_pull` (сам вызов всегда
  требует отдельного подтверждения пользователя).

Если Provider ID и Model ID пусты, используется модель OpenCode по умолчанию.
Provider credentials приложение не читает из OpenCode и не отправляет в prompt.

## Корпоративные источники данных

Публичный проект не содержит URL, auth и формат корпоративных ITSM/ADO API.
Контракты находятся в `opencode_integration/data_sources.py`, а явные точки
подключения — в:

- `services/itsm_service.py`: `ITSMService.get_ticket(ticket_id, environment)`;
- `services/tfs_service.py`: `TfsService.get_pull_request(reference, environment)`.

В открытой версии методы бросают `DataSourceNotConfiguredError`. В корпоративной
сборке нужно заменить их реализацией либо передать реализации `ITSMDataSource` и
`AzureDevOpsDataSource` в `Application(itsm_source=..., ado_source=...)`. AI-код
ничего не знает о внутренних URL или токенах.

## Работа помощника

### Единый чат на главной

Когда три обязательных агента загружены и соединение с OpenCode находится в
состоянии `ready`, на главной появляется чат **Gravitee AI**. Его primary agent
`autodeploy-copilot` является единой точкой входа и умеет:

- определить подходящую форму по заявке и показать три лучших кандидата с
  оценками;
- построить упорядоченный многоформовый план с зависимостями;
- искать API и приложения обычным языком через JSON Repository MCP;
- находить похожие API/приложения как проверяемые шаблоны;
- разобрать ошибку отправки или итог polling, сопоставив её с репозиторием.

Python один раз получает и очищает ITSM/ADO-контекст. Агент сравнивает его с
доверенным компактным каталогом из `config/form_routing.py` и возвращает
закрытый Structured Output. Для одной формы автоматический выбор принимается
только при оценке не ниже 80 и отрыве от второго кандидата не менее 15 пунктов;
в остальных случаях выбор делает пользователь.

Уточнения по одной заявке используют её текущую conversation. При явном переходе
на другой номер заявки приложение удаляет старую OpenCode session, очищает
накопленный MCP provenance и создаёт новую — контексты заявок не смешиваются.

Принятый многошаговый план ничего не исполняет сам. Каждый доступный шаг
открывает обычную форму, проходит тот же `FormExtractorAgent`, Python-validation,
редактируемый preview и ручную отправку. Зависимый шаг разблокируется только
после успешной отправки предыдущего. Подготовленные, но ещё не отправленные
данные шага сохраняются в памяти и могут быть вновь открыты.
Активный план можно отменить, а завершённый — закрыть прямо в чате.

После выбора формы очищенный контекст передаётся в `FormScreen` как одноразовый
handoff. Экран вызывает тот же preview и `apply_form_data`, что и обычная кнопка
**Подтянуть данные из заявки**; ITSM и ADO повторно не запрашиваются.

Поисковые карточки принимаются только если их пара `(scope, x-filepath)` реально
наблюдалась в ответе MCP текущей session. Модель не может придумать источник и
выдать его за найденный. Кнопки диагностики на форме и экране результата
передают в чат только очищенный и ограниченный по размеру payload.

Каталог маршрутизации содержит только назначение форм, признаки использования и
компактный список полей. Это не справочник значений полей, в нём нет reference
ID, токенов или корпоративных данных. При добавлении новой формы для неё нужно
обязательно добавить запись в `FORM_ROUTING`; иначе routing завершается понятной
ошибкой без выбора формы.

### Помощник внутри выбранной формы

Кнопка **Подтянуть данные из заявки** открывает не старый progress-dialog, а
управляемое окно одной OpenCode session:

1. Python получает ITSM-заявку и связанный PR, удаляет секреты и ограничивает
   объём данных.
2. Создаётся session с явно выбранным primary agent `form-extractor`.
3. Агент показывает краткий анализ, пробелы, статусы и вызовы инструментов.
4. Пользователь может отправлять уточнения, отклонять/разрешать MCP-вызовы один
   раз, остановить текущий запрос или отменить всю операцию.
5. Кнопка **Сформировать preview** выполняет отдельный Structured Output запрос.
6. Ответ повторно проходит JSON Schema, доменные проверки и проверку секретов в
   Python.
7. Только после ручного применения preview меняется основная форма.

Скрытый внутренний chain-of-thought модели API не предоставляет. Окно показывает
наблюдаемую часть процесса: сообщения агента, session status, tool status,
permission requests и безопасные диагностические события.

Технические `busy` / `retry` не добавляются в историю как сообщения: они
схлопываются и обновляют одну строку состояния с номером попытки. Главный чат
показывает ID активной session и кнопку открытия этой session в Web UI того же
localhost-сервера. При ошибке session сохраняется для диагностики; отменённая
пользователем и штатно закрытая session удаляется.

## Справочники

Полные справочники больше никогда не входят в prompt или JSON Schema первого
AI-этапа. Модель возвращает подтверждённое контекстом смысловое название,
например `Внешнее АПИ`, но не угадывает ID.

После Structured Output Python локально:

1. загружает только справочники полей текущей формы;
2. сопоставляет название с `value_key`, сначала точно, затем консервативно по
   нормализованному тексту;
3. при неоднозначности оставляет `null` и показывает кандидатов в preview;
4. строит строгую финальную schema с реальными допустимыми ID;
5. повторно валидирует результат.

Тип поля берётся из доверенного описания формы. Для `SELECT` допустимо ровно одно
значение, для `MULTISELECT` — массив уникальных значений; каждое значение массива
разрешается независимо. Если найдено несколько равноправных кандидатов, preview
показывает варианты: выбор кандидата для `MULTISELECT` добавляет ID в список, а
не заменяет весь список и не превращает его в одиночную строку.

Таким образом, каталог из тысяч записей не расходует контекст и не покидает
Python-процесс.

## MCP и границы доступа

`form-router` не получает MCP. `autodeploy-copilot` и `form-extractor` получают
только явно отмеченные пользователем MCP; для выбранного JSON Repository
применяется отдельный точный профиль. Session permissions строятся по принципу
deny-by-default:

- `read`, `glob`, `grep`, `list`, `edit`, `bash`, `task`, web, LSP, skills и
  `external_directory` запрещены;
- разрешён внутренний `StructuredOutput`;
- проверенные инструменты JSON Repository MCP `search_*`, `list_*`, `get_*`
  разрешены по точному списку и запускаются без лишних вопросов; каждый вызов и
  его статус всё равно отображается в чате;
- `git_pull` не находится в auto-allowlist. Если включён соответствующий чекбокс,
  session выставляет ему `ask`, и пользователь решает **каждый вызов отдельно**.
  При выключенном чекбоксе tool остаётся под общим `deny`;
- `diagnose_search` всегда запрещён, так как раскрывает абсолютные локальные пути;
- для read-oriented инструментов прочих выбранных MCP (`get`, `list`, `read`,
  `search`, `query` и аналогичных) действует `ask`;
- инструменты с мутационными именами (`create`, `update`, `delete`, `deploy`,
  `run` и т. п.), а также неизвестные операции остаются под `deny`;
- остальные MCP и инструменты остаются запрещены.

Ни один из агентов не может прочитать YAML с токенами через файловые инструменты —
даже если сервер запущен из другой вкладки или используется также браузером.
`form-router` получает только безопасный каталог назначений форм, а
`form-extractor` — описание полей одной уже выбранной формы. Дополнительно их
runtime физически вынесен за пределы проекта.

Важно: выбранный MCP является отдельной доверительной границей. Нельзя выбирать
filesystem/local-file MCP, если он способен читать локальные секреты. Точный
профиль JSON Repository основан на контракте
`vakaheydev/local-json-repo-mcp` ветки `master`; произвольному стороннему MCP
приложение не может доказать соответствие его имени фактическому поведению.

## Structured Output и сессии

Сообщения главного чата всегда содержат `"agent": "autodeploy-copilot"`, а
сообщения выбранной формы — `"agent": "form-extractor"`. Совместимый старый
маршрутизатор сохраняет явный `"agent": "form-router"`. Structured Output
запрос для OpenCode 1.18.18 передаёт:

```json
{
  "agent": "form-extractor",
  "format": {
    "type": "json_schema",
    "schema": {},
    "retryCount": 2
  }
}
```

Клиент читает фактическое `info.structured` и совместимые имена
`structured_output` / `structuredOutput`. Текст не используется как fallback.
При `StructuredOutputError` preview не открывается, но session остаётся доступна
для уточнения и повторной попытки. После завершения или полной отмены session
удаляется. **Остановить** вызывает abort текущего запроса, не применяя форму.

## Логи

Экран OpenCode содержит живой технический журнал HTTP lifecycle, session,
permissions, tool status и состояний сервера. Ротационный файл —
`logs/autodeploy.log` (5 файлов по 5 MiB); каталог исключён из Git.

Для сервера, созданного формой, stdout/stderr дренируются отдельными потоками и
после фильтрации попадают и в терминал UI, и в файл. Строки, похожие на prompt,
message parts или Structured Output, заменяются служебной отметкой; известные
секреты редактируются, длина строки ограничена. У внешнего общего сервера форма
не владеет процессом и потому логирует только своё HTTP/session/SSE
взаимодействие с ним.

Не логируются prompt/body, необработанный ITSM/ADO-контекст, auth headers и
значения полей формы. Разрешены ID заявки/PR/session, длительность, типы ошибок,
состояния tool-вызовов и агрегированные счётчики.

## Проверки

```bash
python -m unittest discover -s tests -v
python -m compileall -q .
```

Unit-тесты используют временный HTTP server только на `127.0.0.1`. Полный smoke
test требует установленный OpenCode `1.18.18`, настроенный provider и хотя бы
один тестовый корпоративный адаптер. После обновления OpenCode отдельно проверьте
Structured Output и MCP в headless server API до смены целевой версии проекта.
