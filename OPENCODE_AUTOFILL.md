# AI-помощник формы через OpenCode

Интеграция проверена для OpenCode `1.18.18`. Форма может подключиться к уже
работающему общему серверу либо создать собственный `opencode serve`. В обоих
режимах API доступен только как `http://127.0.0.1:<port>`.

## Сервер

Четвёртая карточка **OpenCode** на главном экране содержит две основные кнопки:

- **Подключиться к серверу** — подключиться к адресу из настроек. Такой внешний
  процесс форма никогда не завершает.
- **Создать новый сервер** — проверить `opencode --version`, выбрать свободный
  порт и запустить дочерний процесс:

  ```text
  opencode serve --hostname 127.0.0.1 --port <PORT>
  ```

Для обоих вариантов показываются этапы подключения, адрес, версия, ownership,
PID и состояние агента. Кнопка **Проверить состояние сервера** повторяет
`GET /global/health` и `GET /agent` без создания нового процесса.

При старте приложение автоматически пробует подключиться к
`http://127.0.0.1:4096`. Стандартный connect timeout — 10 секунд; адрес и timeout
изменяются на экране OpenCode. Ошибка отключает только AI-функции.

Созданный формой процесс завершается вместе с приложением. Внешний общий сервер
остаётся работать, поэтому к нему одновременно можно обращаться из формы и из
браузера. Все запросы формы получают отдельный `x-opencode-directory`, а каждая
заявка — отдельную session, поэтому браузерные задачи не смешиваются с формой.

## Конфигурация OpenCode и runtime

Глобальный пользовательский `opencode.json` учитывается самим OpenCode. Поэтому
настроенные в нём provider, model и MCP доступны общему серверу и форме.

При этом форма намеренно не запускает OpenCode из каталога репозитория. Она
использует стабильную отдельную runtime-директорию:

- Linux: `$XDG_DATA_HOME/gravitee-autodeploy-ui/opencode-runtime` либо
  `~/.local/share/gravitee-autodeploy-ui/opencode-runtime`;
- Windows: `%LOCALAPPDATA%\gravitee-autodeploy-ui\opencode-runtime`.

В runtime копируется только `.opencode/agents/form-extractor.md`. Если OpenCode
понадобятся plugin-зависимости, `.opencode/node_modules` появится именно там, а
не в проекте с формой и не рядом с YAML-файлами с токенами. Путь runtime виден
на экране OpenCode.

Настройки формы:

- server URL, Basic Auth username/password и connect timeout;
- startup/request timeout и максимальный размер очищенного контекста;
- необязательная пара Provider ID + Model ID;
- выбранные MCP из списка, который возвращает `GET /mcp`.

Если Provider ID и Model ID пусты, используется модель OpenCode по умолчанию.
Provider credentials приложение не читает из OpenCode и не отправляет в prompt.

## Корпоративные источники данных

Публичный проект не содержит URL, auth и формат корпоративных ITSM/ADO API.
Контракты находятся в `opencode_integration/data_sources.py`, а явные точки
подключения — в:

- `services/itsm_service.py`: `ITSMService.get_ticket(ticket_id, environment)`;
- `services/tfs_service.py`: `TfsService.get_pull_request(reference, environment)`.

В открытой версии методы бросают `DataSourceNotConfiguredError`. В корпоративной
сборке нужно заменить их реализацией либо передать реализации `ITSMDataSource` и
`AzureDevOpsDataSource` в `Application(itsm_source=..., ado_source=...)`. AI-код
ничего не знает о внутренних URL или токенах.

## Работа помощника

Кнопка **Подтянуть данные из заявки** открывает не старый progress-dialog, а
управляемое окно одной OpenCode session:

1. Python получает ITSM-заявку и связанный PR, удаляет секреты и ограничивает
   объём данных.
2. Создаётся session с явно выбранным primary agent `form-extractor`.
3. Агент показывает краткий анализ, пробелы, статусы и вызовы инструментов.
4. Пользователь может отправлять уточнения, отклонять/разрешать MCP-вызовы один
   раз, остановить текущий запрос или отменить всю операцию.
5. Кнопка **Сформировать preview** выполняет отдельный Structured Output запрос.
6. Ответ повторно проходит JSON Schema, доменные проверки и проверку секретов в
   Python.
7. Только после ручного применения preview меняется основная форма.

Скрытый внутренний chain-of-thought модели API не предоставляет. Окно показывает
наблюдаемую часть процесса: сообщения агента, session status, tool status,
permission requests и безопасные диагностические события.

## Справочники

Полные справочники больше никогда не входят в prompt или JSON Schema первого
AI-этапа. Модель возвращает подтверждённое контекстом смысловое название,
например `Внешнее АПИ`, но не угадывает ID.

После Structured Output Python локально:

1. загружает только справочники полей текущей формы;
2. сопоставляет название с `value_key`, сначала точно, затем консервативно по
   нормализованному тексту;
3. при неоднозначности оставляет `null` и показывает кандидатов в preview;
4. строит строгую финальную schema с реальными допустимыми ID;
5. повторно валидирует результат.

Таким образом, каталог из тысяч записей не расходует контекст и не покидает
Python-процесс.

## MCP и границы доступа

По умолчанию агент не получает ни одного MCP. Пользователь явно выбирает только
подключённые глобальные MCP на экране OpenCode. Session permissions строятся по
принципу deny-by-default:

- `read`, `glob`, `grep`, `list`, `edit`, `bash`, `task`, web, LSP, skills и
  `external_directory` запрещены;
- разрешён внутренний `StructuredOutput`;
- для read-oriented инструментов выбранных MCP (`get`, `list`, `read`,
  `search`, `query` и аналогичных) действует `ask`, то есть каждый конкретный
  вызов требует решения пользователя в окне помощника;
- инструменты с мутационными именами (`create`, `update`, `delete`, `deploy`,
  `run` и т. п.), а также неизвестные операции остаются под `deny`;
- остальные MCP и инструменты остаются запрещены.

Агент не имеет прямого доступа к каталогу формы и не может прочитать YAML с
токенами через файловые инструменты — даже если сервер запущен из другой вкладки
или используется также браузером. Дополнительно его runtime физически вынесен
за пределы проекта.

Важно: выбранный MCP является отдельной доверительной границей. Нельзя выбирать
filesystem/local-file MCP, если он способен читать локальные секреты. Системные
правила запрещают агенту использовать MCP для чтения файлов, а интерфейс
показывает запрос и требует подтверждения, но приложение не может доказать, что
произвольный сторонний MCP честно описывает свои возможности.

## Structured Output и сессии

Каждый message явно содержит `"agent": "form-extractor"`. Финальный запрос для
OpenCode 1.18.18 передаёт:

```json
{
  "agent": "form-extractor",
  "format": {
    "type": "json_schema",
    "schema": {},
    "retryCount": 2
  }
}
```

Клиент читает фактическое `info.structured` и совместимые имена
`structured_output` / `structuredOutput`. Текст не используется как fallback.
При `StructuredOutputError` preview не открывается, но session остаётся доступна
для уточнения и повторной попытки. После завершения или полной отмены session
удаляется. **Остановить** вызывает abort текущего запроса, не применяя форму.

## Логи

Экран OpenCode содержит живой технический журнал HTTP lifecycle, session,
permissions и статусов. Ротационный файл — `logs/autodeploy.log` (5 файлов по
5 MiB); каталог исключён из Git.

Не логируются prompt/body, необработанный ITSM/ADO-контекст, stdout/stderr
OpenCode, auth headers и значения полей формы. Форматтер дополнительно редактирует
распространённые секреты. Разрешены ID заявки/PR/session, длительность, типы
ошибок и агрегированные счётчики.

## Проверки

```bash
python -m unittest discover -v
python -m compileall -q .
```

Unit-тесты используют временный HTTP server только на `127.0.0.1`. Полный smoke
test требует установленный OpenCode `1.18.18`, настроенный provider и хотя бы
один тестовый корпоративный адаптер. После обновления OpenCode отдельно проверьте
Structured Output и MCP в headless server API до смены целевой версии проекта.
